# Oracle inference operations — review assets, deployment blocked

No Oracle access, target inspection, model benchmark or deployment has occurred. The scripts and units under `infrastructure/oracle/deploy` prepare an approved Linux/systemd host; paths are installation conventions, not claims about the target. The application API is deployed separately and authenticates users, checks authorization/consent, bounds input and calls the private gateway with its server-only token. Web/native clients never receive that token or call raw runtimes.

## Approval and installation boundary

Complete [the access request](ORACLE_ACCESS_REQUEST.md) and record explicit owner approval for the host, artifact revision, model/license, network changes and maintenance window before any commands below run on Oracle. No installer or remote-connect script is included. Do not overwrite an existing Caddy configuration or alter unrelated services.

On the approved host, inspect OCPU/architecture, free RAM/disk, competing workloads and network rules first. Pin and verify Node, Caddy and one reviewed CPU runtime; install binaries at the unit paths or review path changes. Create an unprivileged `adequate-inference` account with home `/var/lib/adequate-inference` and without interactive login, and a separate `caddy` account. Install reviewed source under root-owned `/opt/adequate-inference`, scripts mode 0755, units root-owned mode 0644, run `npm ci --omit=dev` in the installed root for the gateway’s Zod dependency, install configuration under root-owned `/etc/adequate-inference` mode 0750. Service users must not be able to edit binaries, source, units or configuration.

Copy the three `.env.example` files to their names without `.example`. Replace every placeholder; configuration is plain unquoted `KEY=value`. Keep environment files root-owned mode 0600: systemd reads them before dropping privileges. Generate and store a unique random gateway token of at least 32 characters in the approved secret manager and gateway file. Share it only with the application server. Real values must never enter version control, process command lines or diagnostic output. Runtime services read only `runtime.env`, never the gateway token.

Install approved models under `/var/lib/adequate-inference`: llama.cpp GGUF files should be root-owned, readable by the inference group and immutable to the runtime; only the Ollama model/cache directory is writable by the inference account. Verify model hashes and license approval against the versioned `infrastructure/oracle/registry.json`. Real activation requires a non-proposal version, `license.approved=true`, `artifact.sha256` containing a verified 64-digit SHA-256, and runtime/model/URL matching the active entry; environment overrides cannot switch to a different model. Start with `RUNTIME=mock`. For Ollama select an approved installed `MODEL`, loopback URL `http://127.0.0.1:11434`; for llama.cpp use `RUNTIME=llama.cpp`, URL `http://127.0.0.1:8080`, the verified `MODEL_PATH` and a measured thread budget. Do not enable both runtime units. No script downloads models.

Provide the approved TLS hostname, private/VPN bind address, caller CIDRs and valid certificate chain. Give only the `caddy` group read access to its private key (root:caddy mode 0640), and protect parent directories. `Caddyfile` allows direct clients from the explicit CIDRs and forwards only `/v1/tasks`; the gateway enforces bearer authentication. Health/metrics/admin paths are not exposed by ingress. Caddy admin API and access logging are disabled. Do not enable forwarded-IP trust without a separately reviewed proxy plan. Combine the application allowlist with Oracle NSG/security-list and host-firewall rules; block direct ingress to all raw ports. TLS certificate trust and renewal must be verified from the application network.

Before enablement run shell syntax checks, `systemd-analyze verify` on installed units and `caddy validate --config /etc/adequate-inference/Caddyfile --adapter caddyfile` with the ingress environment loaded securely. Check distro/version support for sandbox and IPAddress restrictions; unsupported restrictions require an approved equivalent firewall control. Do not silently remove hardening. Set measured memory/CPU/task limits in reviewed systemd drop-ins, reserving capacity for existing workloads; no hardware budget is assumed in these examples. Ensure `TimeoutStopSec` exceeds gateway `DEADLINE_MS` plus shutdown overhead (defaults: 35 seconds and 15 seconds).

Only after approval: reload systemd, start the selected runtime, start the gateway, run `scripts/check.sh` as root, then start the dedicated ingress unit. Enable the selected runtime, gateway and ingress at boot only after checks pass. For mock mode, omit runtime startup/enablement. If the approved runtime fails at boot, readiness stays false and the application must use manual flows. A deployment operator should test readiness behavior before enabling ingress.

## Warmup, checks and restart

Runtime `ExecStartPost` calls `warm.sh` with a fixed synthetic prompt; no private user input is sent or logged. Ollama sets `keep_alive=-1`, one loaded model and one parallel request. llama.cpp keeps its server/model process running with CPU-only flags and one slot. Process residency is not a throughput guarantee: verify RSS, headroom and eviction behavior on the actual host. The gateway has one active request, a queue of at most eight and bounded request deadlines; its post-start probe distinguishes readiness from liveness.

`scripts/check.sh` checks loopback liveness/readiness/metrics and rejects unauthenticated task calls. It never prints the token or task payload. On the authorized network, separately verify a trusted TLS connection, authenticated schema-valid synthetic task, expired/invalid token rejection, disallowed caller denial and refusal of raw-port access. Inspect `ss -ltnp` on the host; raw listeners must show `127.0.0.1`, not a wildcard. Raw runtime stdout/stderr is suppressed by default, Ollama debug is disabled, and llama.cpp uses the reviewed `--log-disable` flag; verify support with the pinned runtime before installation. Gateway logs contain metadata only. Verify private task inputs/outputs and authorization headers do not appear in journald or application logs, and do not enable upstream verbose/prompt logging. Monitor queue depth/deadlines/circuit state, warm latency, CPU/RSS, disk, uptime and certificate expiry with payload-free identifiers.

For an approved maintenance change, run `/opt/adequate-inference/infrastructure/oracle/deploy/scripts/restart.sh --change-id APPROVED_CHANGE_ID` as root. The ID records authorization; the script cannot grant it. It stops the gateway first: SIGTERM refuses new tasks and drains active work within the request deadline before exit. It then restarts/warms the selected runtime, starts the gateway, waits for readiness and checks authentication. Caddy remains running; upstream downtime returns an unavailable response. If a step fails, the script exits and leaves the gateway stopped rather than presenting a cold runtime as ready. Investigate metadata-only logs, restore the reviewed runtime/model/config revision, then start and check the gateway. Avoid restarting the runtime directly during active requests.

Rehearse recovery, reboot, warmup and graceful drain with authorized synthetic workload before acceptance. Back up reviewed configuration/model manifest and approved source revision; keep secrets encrypted in the secret manager, separate from source backups. Restore into an isolated environment first. Model caches can be rebuilt only from approved verified artifacts. Gateway/runtimes must never publish, change permissions or execute model-suggested tools.

## Application continuity and pending verification

When timeout, queue rejection, cold startup, circuit opening or maintenance makes it unavailable, retain the user's manual reflection/draft and let manual editing, deterministic search and playback continue. Show an honest unavailable state; do not mutate saved text, infer hidden consent or silently send private material to an external model. Retry only by explicit user action or a bounded approved policy.

Local syntax/text checks do not prove host readiness. Caddy parsing against real TLS files, installed-unit verification, firewall/VPN enforcement, SSH authorization, resource budgets, model licensing, residency, actual p50/p95 latency, restart/reboot recovery, alerts and backup restoration remain blocked pending access and explicit approval.
